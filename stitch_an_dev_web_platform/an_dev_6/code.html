01 // CONTEXT

المعضلة وسياق المشروع (The Context)

كنا ندير منصة خدمات مالية وإدارية تعمل في السوق المحلي الجزائري. البنية الأساسية اعتمدت على حاوية Node.js منفصلة وخادم PostgreSQL مدار سحابياً. بالرغم من أن استعلامات SQL الفردية كانت تستغرق أقل من 3 ميلي ثانية داخل محرك قاعدة البيانات، إلا أن زمن استجابة الـ Endpoints كان يتراوح دائماً بين 65ms و120ms.

عند تحليل أداء الشبكة (Flamegraphs) والـ Tracing بواسطة OpenTelemetry، اكتشفنا ما يسمى بـ ضريبة زمن اتصال الشبكة (Network Latency Tax): فكل عملية طلب للواجهة كانت تقوم بـ 3 إلى 5 استعلامات غير متزامنة، مما أدى إلى ضياع أكثر من 60% من وقت الاستجابة فقط في تبادل حزم TCP/IP والمصافحة المشفرة عبر شبكة الخوادم.

02 // BENCHMARKING

المقارنة المعمارية: Postgres vs SQLite

SQLite ليست مجرد لعبة للهواتف الذكية أو بيئات الاختبار والتطوير؛ إنها مكتبة C مدمجة داخل مساحة ذاكرة التطبيق (In-process memory mapped C library). لا توجد مقابس شبكة، لا يوجد تشفير TLS داخلي يستهلك دورات المعالج، والاستعلام يتم باستدعاء دوال مباشرة في الذاكرة.

جدول القياسات التجريبية تحت حمل 500 مستخدم متزامن ENVIRONMENT: ALGERIA VPS (4 vCPU, 8GB RAM)
المعيار الهندسي PostgreSQL 16 (شبكي) SQLite 3 (نمط WAL مدمج)
زمن الاستعلام الفردي (Query RTT) 16.4 ms (عبر Socket) 0.08 ms (استدعاء ذاكرة)
متوسط استهلاك الذاكرة العاطلة (RAM) ~148 MB ~11 MB
معدل الطلبات/ثانية (Throughput) 3,850 req/sec 42,400 req/sec
زمن استجابة الـ API التراكمي (p95) 84.2 ms 14.1 ms

03 // ENGINE CONFIG

تهيئة WAL وPragmas للإنتاج الفعلي

الافتراض الشائع هو أن SQLite تُغلق الملف بالكامل عند كل عملية كتابة مما يمنع القراءة. هذا صحيح فقط في وضع الاسترجاع التقليدي (Rollback Journal). ولكن بتفعيل نمط WAL (Write-Ahead Logging)، يتحول السلوك الهندسي جذرياً: القراءات لا تعطل الكتابات، والكتابات لا تعطل القراءات مطلقاً.

للوصول إلى إنتاجية حقيقية تتحمل مئات العمليات بالثانية، قمنا بضبط الأوامر التحضيرية الأساسية (Pragmas) مباشرة عند لحظة الاتصال:

  • PRAGMA journal_mode = WAL; يتيح التزامن العالي بين خيوط المعالجة.
  • PRAGMA synchronous = NORMAL; يوازن بين ضمان سلامة البيانات وأداء كتابة القرص NVMe دون استدعاء fsync دوري قاتل للأداء.
  • PRAGMA cache_size = -64000; يخصص ما يقارب 64 ميجابايت من الذاكرة العشوائية لصفحات الفهرسة السريعة.
  • PRAGMA mmap_size = 2147483648; يفعّل تعيين الملف مباشرة بالذاكرة حتى 2GB.
04 // IMPLEMENTATION

كود Fastify وDrizzle ORM التطبيقي

إليكم الكود المعتمد فعلياً داخل طبقة البيانات باستخدام Fastify وBetter-SQLite3 مع Drizzle ORM:

fastify-sqlite-db.ts 
// Initializing high-throughput SQLite engine for Fastify
import Database from 'better-sqlite3';
import { drizzle } from 'drizzle-orm/better-sqlite3';
import path from 'node:path';

const dbPath = path.resolve(process.env.DB_FILE_PATH || '/data/production.db');

// 1. Open instance with strict concurrency profile
const sqlite = new Database(dbPath, {
  fileMustExist: false,
  timeout: 5000, // Auto busy timeout before throwing SQLITE_BUSY
});

// 2. Enforce aggressive enterprise production pragmas
sqlite.pragma('journal_mode = WAL');
sqlite.pragma('synchronous = NORMAL');
sqlite.pragma('temp_store = MEMORY');
sqlite.pragma('cache_size = -64000'); // 64MB In-RAM index cache
sqlite.pragma('mmap_size = 2147483648'); // 2GB memory-mapped I/O
sqlite.pragma('foreign_keys = ON');

// 3. Wrap with type-safe Drizzle ORM instance
export const db = drizzle(sqlite);
export const rawClient = sqlite;
05 // REPLICATION

النسخ الاحتياطي المباشر عبر Litestream

السؤال الأكثر شيوعاً الذي يطرحه أي مهندس متمرس: "ماذا لو انهار الخادم الفعلي أو تعطل القرص الصلب؟" هنا يبرز دور أداة Litestream الرائعة. تعمل Litestream كـ Daemon خفيف للغاية يراقب ملف الـ WAL في الخلفية، ويقوم بترحيل التغييرات ثانية بثانية وبشكل مستمر (Continuous WAL Streaming) إلى أي مزود تخزين كائنات (S3-Compatible / MinIO).
